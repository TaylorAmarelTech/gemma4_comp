Getting started

A safety harness around Gemma 4 for migrant-worker recruitment and trafficking. This kernel ships a baseline catalog of -- GREP rules, -- RAG docs, and a knowledge taxonomy spanning 6 branches and 21 leaf types. From this kernel you can chat with Gemma 4, compare harness configs, process case bundles, draft new knowledge, search the web through a sanitization layer, and sync vetted knowledge from the public hub.

1. Quick start

The shortest path from a fresh kernel to a graded comparison:

Step 1

Open Chat and load a model

Open Chat. On first visit a model picker appears: pick a Gemma 4 variant and wait for it to load. Smaller variants load in under a minute; larger ones can take several minutes on a first run.

Step 2

Try an example

Once the model is ready, flip the GREP / RAG / Tools / Online toggles and pick a prompt from the examples dropdown (for example "Passport retention" or "Placement fee"). Watch the harness layers fire in the activity log.

Step 3

Compare configs

Switch to Compare, pick the stock-vs-full preset, click Run. See the same prompt with and without the harness, side by side.

Step 4

Grade both

Scroll to the bottom of Compare and click Grade both. The Universal v3 rubric returns a 0-100 score for each variant so the lift is quantitative, not anecdotal.

Step 5

Process a sample

Go to Process Files, click Use sample. See GREP rule firings and entity extraction on a small case bundle.

Step 6

Check Status

Visit Status for live counts of knowledge objects, sync history, model state, and search backend wiring.

2. Architecture & data flow

Every user-facing surface in the kernel is a harness: a self-contained module that registers FastAPI routes, declares the knowledge types it consumes and emits, and writes per-task audit JSONL to /kaggle/working/training/<harness>.jsonl. Safety layers (Persona, GREP, RAG, Tools, Online) are composed per harness. Chat uses all five, Extraction uses Persona + GREP + RAG, and Anonymization runs no layers because it is a safety layer.

3. The 7 harnesses

Each harness exports a fixed contract (name, applied_layers, consumes, emits, register_routes). The five PRIMARY harnesses are the user-named safety surfaces; the two SECONDARY harnesses are utility/CRUD surfaces.

chat PRIMARY applied_layers: persona, grep, rag, tools, online

Free-form multi-turn chat with the loaded Gemma 4. The richest harness: all five safety layers compose into a single response. Optional image upload for multimodal prompts.

POST /api/chat/send (SSE) · POST /api/chat/upload-image · GET /api/chat/image/{sid}
process PRIMARY applied_layers: grep, rag, tools

Bulk-process an uploaded bundle (ZIP, CSV, JSONL). Each row passes through the GREP layer and an entity extractor (amounts, phone numbers, email addresses, statute references, recruitment corridors). The harness builds a local knowledge graph from the bundle so you can chat against the parsed contents.

POST /api/process/batch · POST /api/process/graph-chat
extraction PRIMARY applied_layers: grep, rag

Drafts a standardized knowledge-object envelope from raw text. Pick a target leaf type (grep_rule / rag_doc / context_snippet / ...) and Gemma 4 produces a validated envelope that can be promoted into the local knowledge store.

POST /api/knowledge/draft-envelope
anonymization PRIMARY applied_layers: () is a safety layer

Hard gate. Detects PII via regex + NER and redacts before any data crosses a trust boundary. The audit log stores sha256(original), never plaintext. Owns the hub-submission flow.

POST /api/anonymize · POST /api/submit/knowledge · POST /api/submit/local
search_safety PRIMARY applied_layers: () is a safety layer

Intercepts outbound search queries before they reach any third-party backend. Strips emails, phone numbers, passport numbers, IBANs, monetary amounts, URLs, and national IDs. Optionally asks Gemma to rephrase the redacted query into a more general form.

POST /api/search/sanitize · GET /api/search/safety-info
search SECONDARY applied_layers: ()

Web search via SearXNG (preferred, privacy-preserving) or Tavily / Brave / DuckDuckGo / Wikipedia as fallbacks. Always called AFTER search_safety sanitizes the query when the page-side toggle is on.

POST /api/search/client · POST /api/search/server · GET /api/search/backends
import_corpus SECONDARY applied_layers: ()

CRUD over user-attached evidence. Drag-drop a file, paste a snippet, list and delete imports. No LLM call; pure file storage with audit metadata.

POST /api/import/upload · POST /api/import/snippet · GET /api/import/list · GET / DELETE /api/import/{doc_id}

5. Knowledge object taxonomy (6 branches, 21 leaves)

Every persisted artefact in /kaggle/working/knowledge/ conforms to a v1.0 envelope: {schema_version:"1.0", knowledge_object_type:<leaf>, id:<kebab>, content:{...}}. Six branches partition the 21 leaf types:

matching_knowledge

4 leaves

grep_rule, glob_rule, classifier_rule, heuristic_rule -- patterns that match input to a label/category.

grounding_knowledge

4 leaves

rag_doc, citation_edge, corridor_profile, ngo_directory -- statutes, NGO contacts, statute-to-statute relations.

reasoning_knowledge

4 leaves

persona_block, context_snippet, reasoning_step, rubric_dimension -- how the model should think through a problem.

tool_knowledge

3 leaves

tool_definition, tool_example, tool_chain -- function-calling specs and example invocations.

input_knowledge

3 leaves

fact_template, upload_schema, prompt_template -- shapes user input must take to be ingestible.

output_knowledge

3 leaves

envelope_schema, audit_template, submission_schema -- shapes the system outputs to downstream consumers.

Live counts on this kernel: checking..., checking.... See Status for the per-leaf breakdown.

   +========================================================================+
                                      |
                                      |  outbound only (and only via the
                                      |  surfaces above, with PII stripped)
                                      v
              +------------------+              +------------------+
              | SearXNG/Brave/   |              |  DueCare hub     |
              | Tavily/DDG       |              |  (public         |
              | (search backend) |              |  knowledge)      |
              +------------------+              +------------------+
  • Browser <-> Kernel: HTTPS via Cloudflared. Only your laptop sees it (or whoever has the tunnel URL).
  • Kernel -> Search backend: opt-in per search; only the sanitized query flows (sanitize toggle defaults ON in Search).
  • Kernel -> DueCare hub: outbound GET only on Sync (pulls vetted envelopes). The hub does NOT see anything on this kernel unless you go through Anonymization & Sharing and explicitly submit a redacted artefact.

Never logged in plaintext: raw chat messages, raw uploads, raw search queries. The training-data JSONL streams under /kaggle/working/training/ use sha256 fingerprints, not raw content.

7. API endpoint reference

Every route the kernel exposes, grouped by purpose:

Chat surface

  • POST /api/chat/send -- SSE stream of step events + final response
  • POST /api/chat/upload-image -- attach image for multimodal prompts
  • GET /api/chat/image/{sid} -- serve a previously-uploaded image

Grading

  • POST /api/grade -- deterministic rubric grader (rules-based, fast)
  • POST /api/grade-deep -- Gemma-as-judge over each rubric dimension
  • POST /api/grade-combined -- weighted blend of both
  • POST /api/grade-deep-stream, /api/grade-combined-stream -- SSE versions for slow runs

Process & ingestion

  • POST /api/process/batch -- multipart bundle upload
  • POST /api/process/graph-chat -- chat against the local knowledge graph
  • POST /api/import/upload, POST /api/import/snippet -- attach evidence
  • GET /api/import/list, GET/DELETE /api/import/{doc_id} -- evidence CRUD

Knowledge object pipeline

  • POST /api/knowledge/draft-envelope -- Gemma drafts a typed envelope
  • POST /api/knowledge/promote -- persist a validated envelope
  • POST /api/knowledge/import -- multipart ZIP bundle import
  • POST /api/knowledge/sync -- pull vetted+unvetted from hub
  • GET /api/knowledge/list, GET /api/knowledge/{type}/{id} -- inspect
  • GET /api/knowledge/export -- export the local store
  • GET /api/knowledge/taxonomy -- the live 21-leaf catalog

Anonymization & submission

  • POST /api/anonymize -- redact text via regex + NER
  • POST /api/submit/knowledge -- submit a redacted artefact to the hub
  • POST /api/submit/local -- legacy alias

Search (PII-safe by default)

  • POST /api/search/sanitize -- strip PII from a query (sanitize harness)
  • GET /api/search/safety-info -- which sanitization modes are wired
  • POST /api/search/client, POST /api/search/server -- execute search
  • GET /api/search/backends -- list available backends + availability

Configuration & introspection

  • GET /api/harness/inventory -- baseline counts (built-in GREP/RAG/...)
  • GET /api/harness-info -- per-layer wiring flags
  • GET /api/harness-catalog/{layer} -- drill-in for a single layer
  • GET /api/version, GET /api/model-info -- kernel/model state
  • GET/POST /api/retrieval/config -- RAG knobs (BM25, rerank, parent-expand)
  • GET/POST /api/online/config, POST /api/online/test -- search BYOK
  • GET /api/dc-logs, GET /api/dc-logs/stats, POST /api/dc-logs/clear -- structured logs

8. Common workflows

A. Stock-vs-harness comparison for the demo video

  1. Open Compare.
  2. Click the stock vs full preset.
  3. Pick "Passport retention (Saudi)" from the examples dropdown.
  4. Click Run comparison. Variant A returns a generic Gemma answer; Variant B returns the harnessed answer with GREP rule firings and statute citations.
  5. Click Grade both. Variant B typically scores 70-90, Variant A 30-50.
  6. Take a screenshot of the side-by-side view for the demo reel.

B. Onboard a new NGO's local knowledge

  1. Have the NGO export their case files as a ZIP.
  2. Drop the ZIP on Process Files; review the GREP/entity output.
  3. For unmodeled patterns, paste excerpts into Knowledge Extraction with target_leaf=grep_rule; Gemma drafts a candidate rule.
  4. On Anonymization & Sharing, redact + submit the new rules to the public hub.
  5. The hub vetting queue surfaces them to reviewers; once vetted, every DueCare kernel that runs Sync picks them up.

C. Safe web research for a worker case

  1. Open Search; keep Sanitize query before sending ON.
  2. Paste a query that might contain PII (e.g., a worker name or passport number).
  3. Click Search. The sanitize-preview panel shows exactly what was redacted before dispatch.
  4. Review results; click Draft as knowledge objects to convert relevant pages into rag_doc envelopes via Gemma.
  5. Click Send to Anonymization & Share to queue the drafts for hub submission.

9. FAQ & troubleshooting

The activity log on a page is empty.

Click the action button (Run, Search, Process, etc.) -- the log only fills as events arrive. If the page itself hasn't done anything yet, the log is intentionally idle. If the log stays empty after a successful action, hit hard-refresh (Ctrl+Shift+R) -- there was a race that's now fixed but stale browser caches can still hit it.

A response is cut off mid-sentence.

On Compare, the default is 16384 tokens; raise max_new_tokens in section 3. On Chat, click the generation-config gear next to the composer.

The Online layer says "not wired" on a kernel.

Open Settings → Online search and provide a Brave or Tavily API key (BYOK). Alternatively, set DUECARE_SEARXNG_URL in the kernel env so the kernel reaches your self-hosted SearXNG.

Where do my synced or imported knowledge objects show up?

Globally: any harness that consumes the leaf type the new object uses picks it up on the next prompt. See the consume/emit map on Status. No kernel restart needed.

Can I disable the search-safety harness?

You can flip the page-side toggle off on Search, but the search.html UI strongly discourages this. The harness exists because queries leave the kernel; once they do, you can't take them back. If you have a use case for sending raw queries (e.g., looking up a public statute URL), turn it off for that single query.

How do I freeze the kernel for final submission?

Run python scripts/freeze_kernels_for_submission.py. It flips configs/submission_freeze.json to frozen=true and re-pins every kernel's install path to an immutable SHA. The install-policy test will then reject any moving-ref (master / main / HEAD) install.
